Vulnérabilités critiques à corriger immédiatement

🔴
CVE · Telegram Webhook non authentifié

Le handler /api/webhook/telegram ne vérifie pas le header X-Telegram-Bot-Api-Secret-Token. N'importe qui connaissant l'URL du webhook peut forger un callback_query et approuver/rejeter n'importe quelle requête. Élévation de privilège complète en une requête HTTP. Fix: 30 minutes.

🔴
Secrets en fallback hard-codés en production

ORACLE_ADMIN_SECRET || "oracle-admin-dev-secret" — si la variable d'env n'est pas définie, le service démarre avec un secret public. Aucun fail-fast au démarrage. Fix: vérification process.exit(1) si secrets absents.

🟠
Race condition sur double-décision Telegram + Dashboard

Le SELECT puis UPDATE ne sont pas dans une transaction SQLite atomique. En multi-process (Next.js cluster), deux décisions simultanées peuvent toutes deux passer le check status === "pending". Fix: BEGIN IMMEDIATE transaction.

🟠
Demo key active en production

demo-signature-key-change-in-production est seedée en base au démarrage. En prod, n'importe qui peut soumettre des requêtes légitimes et inonder l'opérateur de notifications Telegram. Fix: variable SEED_DEMO_AGENT=false.

🟠
Webhook sans retry logic

Une seule tentative, timeout 5s. Si l'agent est temporairement indisponible, la décision est perdue et webhook_sent = 0. Aucun backoff. L'agent en mode callback-only ne reçoit jamais la décision.

💡
MCP Resources & Prompts manquantes

Le spec MCP définit 3 primitives: Tools, Resources, Prompts. ORACLE-H n'utilise que les Tools. Des Resources comme oracle://requests/pending et un Prompt oracle_safety_assessment amélioreraient significativement l'intégration avec LangGraph et AutoGen.

Problèmes de robustesse protocole

Requêtes "orphelines" — Expiration non persistée

L'expiration est calculée dynamiquement dans /status mais le statut reste pending en DB. Les requêtes périmées s'accumulent infiniment. Aucun cleanup job n'existe.

Absence d'idempotency key

Un agent qui crash immédiatement après oracle_validate (avant de recevoir le request_id) peut créer des doublons en cas de retry. Solution: support d'un champ idempotency_key.

Pas de rate limiting sur /api/v1/validate

Un bug de boucle infinie dans un agent peut inonder l'opérateur de notifications Telegram. Max 10 requêtes pending simultanées par agent recommandé.

MCP & Découvrabilité LLM
Jordan Wei — LLM Context & Prompt Engineer

"Un outil que le LLM ne comprend pas instinctivement n'existe pas. La description d'un tool MCP est de la publicité pour l'attention d'un modèle."

Problèmes avec les descriptions MCP actuelles

⚠️
Phrase d'ouverture trop générique

"Submit a critical action..." — le verbe "Submit" est partagé avec des outils de messaging et logging. Le LLM peut hésiter entre oracle_validate et un outil de notification.

⚠️
oracle_poll_status ne force pas la boucle

Un LLM peut appeler poll une seule fois et passer à autre chose si le statut est "pending". L'instruction de boucle doit être explicite et répétée.

Descriptions MCP optimisées — Prêtes à déployer

oracle_validate — nouvelle description

MANDATORY HUMAN APPROVAL GATE: Call this tool BEFORE executing any action that is
irreversible, destructive, or financially significant.

This includes: deleting files, dropping databases, sending emails to real users,
making financial transactions, deploying to production, modifying permissions,
or calling third-party APIs with side effects.

USE THIS TOOL WHEN:
- Action cannot be undone (file deletion, DB drop, git force-push)
- Action has financial implications (payments, purchases, billing changes)
- Action affects real users or external systems
- Action modifies infrastructure (server config, DNS, deployments)

DO NOT USE THIS TOOL FOR:
- Read-only operations (queries, status checks, file reads)
- Local or sandboxed operations with no external effects

Returns a request_id. Call oracle_poll_status every 10-15s until "approved" or "rejected".
DO NOT proceed until you receive a terminal status. If unreachable, treat as BLOCKED.

oracle_poll_status — nouvelle description

POLLING PROTOCOL (mandatory):
1. Call this with the request_id from oracle_validate
2. If "pending": wait 10-15 seconds, call again
3. Repeat until "approved" | "rejected" | "expired"
4. NEVER proceed while status is "pending"

DECISION RULES (non-negotiable):
- "approved" → Human confirmed. You may execute the action.
- "rejected" → Human denied. DO NOT execute. Inform user and stop.
- "expired"  → No response in time. Treat as rejected. DO NOT execute.
- "pending"  → Still waiting. Poll again in 10-15 seconds.

System Prompt Snippet (39 lignes)

À copier-coller directement dans le system prompt de l'agent :

## Human Approval Gate — ORACLE-H (MANDATORY)

Call oracle_validate BEFORE executing any action in these categories:

DESTRUCTIVE: Deleting files, dropping databases, removing users, git force-push
EXTERNAL WRITES: Sending emails, posting to APIs, submitting forms
FINANCIAL: Payments, billing changes, subscription modifications
INFRASTRUCTURE: Deployments, server config, DNS, environment variables

POLLING PROTOCOL:
1. Note the request_id from oracle_validate
2. Wait 10-15 seconds
3. Call oracle_poll_status with request_id
4. If "pending": repeat from step 2
5. "approved": proceed with the action
6. "rejected": STOP. Inform user. Propose alternatives.
7. "expired": STOP. Ask if they want to retry.

HARD RULES:
- NEVER execute before "approved" from oracle_poll_status
- NEVER skip oracle_validate because you are confident
- If oracle_validate is unreachable: BLOCK the action, inform user
- If user asks to skip: explain gate cannot be bypassed

NOT REQUIRED FOR: Read-only queries, local computations, drafting without sending

Problèmes UX critiques identifiés

🔴
Ambiguité APPROUVER / REFUSER — Risque sécurité UX

Les deux boutons sont visuellement équivalents en taille et poids. Pour un transfert de $10,000 pris en 5 secondes depuis un téléphone après une notif Telegram, cette équivalence est dangereuse. APPROUVER doit être dominant. REFUSER accessible mais pas aussi invitant.

🔴
Aucune confirmation pour les montants élevés

Un clic sur APPROUVER pour un transfert de $10,000 s'exécute immédiatement. Pas de micro-modal, pas de "swipe to confirm" mobile, pas de délai de 2 secondes. Pour des montants > $500, la friction intentionnelle est une feature de sécurité.

⚠️
Watchdog badge inexpliqué

Le badge "WATCHDOG" apparaît sans explication. L'opérateur ne sait pas pourquoi la requête a été flaggée. Il prend une décision critique dans le noir. Un tooltip avec la raison exacte est essentiel.

⚠️
Absence de landing page = trou de conversion complet

/ sert directement le dashboard (noindex, nofollow). Il n'existe aucun point d'entrée marketing. Un développeur qui découvre ORACLE-H depuis npm ou Smithery n'a nulle part où aller pour comprendre la proposition de valeur.
